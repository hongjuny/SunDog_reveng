# SHIP 포인터, 보행, 행동 판정

Play segment 15의 SHIP에서는 **포인터 좌표와 주인공 좌표가 별개**다. 조이스틱으로 포인터를 옮기는 것만으로 주인공이 이동하지 않는다. 버튼 0을 누르는 동안 주인공이 포인터 쪽으로 보행하고, 버튼을 놓으면 **주인공의 현재 위치**로 시설 행동을 판정한다. 이는 원본 제어 흐름으로 확인했으며, 실제 게임의 시간별 입력을 녹화한 결과는 아니다.

## 근거와 재현

`python3 tools/ship_action_evidence.py`가 원본 segment SHA와 디코더 경계를 검사하고 `analysis/ship-actions.json`을 생성한다. 비공개 원본 p-code P14를 허용 명령만으로 제한 실행하여 번역한 판정식과 45,220개 좌표/장비 조건을 대조한다. 원본 바이트와 전체 디스어셈블은 저장소 공개 파일에 복사하지 않는다. JSON의 각 근거에는 Play 논리 track/sector, 이미지 바이트 위치, segment 내 범위, SHA가 있다.

| 역할 | 근거 | 확신 |
|---|---|---|
| 포인터 x/y | P1 `099F–09A3`, root local 3/2에 library22 P43 결과 | 높음 |
| 주인공 x/y | P11 `05C7–05D3`, save word40 / word41 low8 → root local6/5; P15 `08C9–08D7` 역방향 저장 | 높음 |
| 보행 유지 | P1 `0995–099D`, `09E2–09EA`, selector4 참이면 P13 | 높음 |
| 놓을 때 행동 | P1 `09EC–0A03`, level0 변화를 기록하고 false이면 P16 | 높음 |
| 두 번째 버튼 | P1 `09A6–09BB`, selector1 또는 mode10이면 P15 후 segment8 P1 | 높음 |
| 위치 행동 판정 | P16 `08E6–08F0`의 인자는 주인공6/5, P14 결과를 action ID로 사용 | 높음 |

버튼 selector의 실제 장치 의미와 포인터 XOR 처리는 별도 입력 분석 근거와 함께 읽어야 한다. P13은 이동 전후에 P41을 호출하여 포인터를 지우고 다시 그린다. 이 호출이 보행 좌표를 뜻하지 않는다.

## 보행과 충돌

P13 `070C–0767`: `dx=pointerX−3−actorX`, `dy=pointerY+3−actorY`. 각 축은 부호를 유지하며 절댓값 최대 2로 제한한다. library22 P34는 sign, P35는 abs인 **p-code**다. 고정된 프레임 속도나 초당 픽셀 수는 아직 측정하지 않았다.

P13 `077C–078A`는 sprite ID 12,13과 dx,dy,주인공 좌표 주소를 library22 P22에 전달한다. P22의 원본 archive entry는 `14FE`, 비교용 relocation base `$4000`에서는 `$54FE`다. 이는 실제 런타임 고정 주소를 주장하지 않는 정규화 주소다. 원본 native는 다음 순서로 후보를 검사한다.

1. `(x+dx,y+dy)`
2. `(x+dx,y)`
3. `(x,y+dy)`

첫 충돌 없는 후보에서 좌표를 기록하고 나머지 후보 검사를 생략한다. 세 후보가 모두 막히면 좌표를 유지한다. P13 `078D–07B2`는 좌표 두 개가 모두 그대로일 때만 최대 1픽셀 단위로 P22를 재호출한다. 따라서 벽을 따라 한 축으로 미끄러지는 동작이 제어 흐름에 들어 있다.

P22는 P9의 mode2를 충돌 검사로 사용한다. P9 정규화 `$5470–54BC`는 sprite의 low7 비트와 화면 바이트/마스크를 AND하고 겹침이 있으면 `$9000`을 증가시킨다. P22 `$557B–5580`은 이 값이 0일 때만 이동을 승인한다. 별도의 타일 walk-map을 읽는다는 증거는 확보하지 않았다. 어떤 원본 sprite/배경/색 마스크가 각 상황에서 통과 가능성을 만드는지까지 검증하려면 실제 자원 배치와 P9 전체 재현이 필요하다.

REA/Ghidra의 원본 Utility 메모리 배치에서도 P22 재확인: `$AABC–AB82`, memory segment base `$95BE`; evidence ID `ev_4d639db5476cf53d2fd3134f0c34c92d65ccb6e5bd4575c40a1c0c0de2923fe8`, SHA-256 `1307ab43ea5af86dc593aca34ab5cedb83404233812557756e0ffa114613e7e4`. 원본 응답은 `analysis/local/rea/ship-move22.json`에 비공개 보존한다.

### 구체적인 입력 → 효과 검사

통제된 fixture에서 actor `(48,114)`, pointer `(53,112)`를 주면 P13 수식은 `(dx,dy)=(2,1)`이다. **원본 P22의 6502 바이트를 실행**한 결과:

| 명시적으로 주입한 충돌 후보 | 실제 원본 P22 좌표 결과 |
|---|---|
| 없음 | `(50,115)` |
| `(50,115)` | `(50,114)` |
| 위 둘 | `(48,115)` |
| 위 셋 | `(48,114)` 유지 |

이 검사는 P9를 합성 충돌 응답으로 가로채는 제한된 native probe다. 실제 SunDog 장면에서 해당 점이 통과 가능하다는 주장이나 실시간 조이스틱 관측은 아니다. 좌표 저장, 후보 순서, 성공 시 즉시 반환, 스택 정리는 원본 P22가 직접 실행한다.

## 놓을 때 시설 판정

P14는 주인공 anchor `(x,y)`를 `column=trunc((x+3)/7)`, `row=trunc((y−3)/8)`로 바꾼다. 음수 나눗셈은 0쪽 절삭이다. 기본 ID는 0이다.

| column | row → ID | 추가 조건 |
|---|---|---|
| 6 | 12 → 1 | 없음 |
| 8 | 14 → 4, 10 → 6 | ID4는 `(word38&63)+(word39&31)>0` |
| 12 | 13 → 5 | 없음 |
| 14 | 14 → 3 | 같은 장비 수 조건 |
| 16 | 8 → 10, 16 → 11, 18 → 13 | 그 외 `trunc((y−5)/8)==6`이면 ID8 |
| 17 | 15 → 7, 7 → 9, 17 → 12 | 없음 |

예를 들어 actor `(39,99)`이면 column6,row12 → ID1이다. P16은 이전 action ID와 같으면 nonlocal EXIT로 중복 실행을 억제한다. 새 ID1이면 P15가 주인공 위치를 저장하고 packed mode를 0으로 바꾸며 P4의 조종석 계기 렌더링으로 넘어간다. **포인터만 `(39,99)`에 놓았다고 실행되는 경로는 아니다.**

더 직접적인 현재 디스크 근거: Utility 선택 slot1, absolute block37의 word40=42, word41=103이므로 Bowie의 저장된 주인공은 `(42,103)`이다. state `0x32BB`의 previous-mode11은 P11 case `062A→05C7`로 이 좌표를 복원하고 previous-action을 0으로 둔다. 이 위치는 column6,row12여서 ID1이다. 포인터가 `(45,100)`이면 이동 delta가 `(0,0)`이므로, 이 조건에서 버튼0을 눌렀다 놓는 흐름은 주인공 이동 없이도 새 ID1 → mode0 → 조종석으로 이어진다. 이는 실제 저장 데이터와 원본 분기를 연결한 **조건부 추적**이며 live 입력 캡처는 아니다. 저장 데이터의 sector와 SHA도 JSON에 보존한다.

ID3은 P7, ID4는 P6으로 분기하며 둘 다 mode3 전환 코드를 갖는다. P6은 word347 조건에 따라 mode 변경을 건너뛰고 actorY에 20을 더한다. 나머지 양수 ID는 word347이 false이면 segment14 P1로 ID 주소를 넘긴다. 시설 명칭을 이 숫자만으로 정하지 않았다. ID5–13 메뉴의 완전한 이름/효과, 두 조건부 출입구의 게임상 의미, 실제 자원 기반 충돌과 보행 속도는 남은 과제다.
